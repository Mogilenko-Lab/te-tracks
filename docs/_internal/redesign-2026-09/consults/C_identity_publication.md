# Unit C — one identity, immutable snapshots, one pointer

**Decision:** use one release-scoped `BUILD_ID`, explicit fragment/group/taxonomy keys, and permanent `archive/<full BUILD_ID>/` directories. `current` selects one complete directory. Nothing moves when it becomes old.

Citations below use `T/` = `/workspaces/Meta-Aging/01_modules/te-tracks/`, `A` = `/workspaces/Meta-Aging/_scratch/te-tracks-audit/report/AUDIT.md`, and `O` = `/workspaces/Meta-Aging/_scratch/te-tracks-audit/consult/fanout/owner_context_2026-09-15.md`. Recommendations describe proposed behaviour, not existing implementation.

## 1. Identity and the ledger

**Premise:** the owner needs reference-build × fragment identity and feature registration at explicit resolutions (O:35–42). **Implication:** one release id is sufficient; adding an export produces a new release scope even when its canonical rows are unchanged. **Caveat:** equality across releases requires comparing the canonical file checksums or an explicit record comparison; identical selfdesc strings alone do not establish identical annotations.

**Definition:** `BUILD_ID` is SHA-256 of the UTF-8, newline-terminated list of `"<lowercase file md5>  <relative path>"`, sorted by relative path in C order, covering every delivered data file **and the deterministic `MANIFEST.json`**, excluding `BUILD_ID` itself and retained `source/` bytes.

Including the manifest is a deliberate revision of the existing fingerprint, which excludes it (T/src/release.sh:21–30). It binds source identity, schema and policy to the release without a second annotation hash or another provenance file. No build id appears inside the manifest or hashed tables: the directory supplies release scope, and ledger ingestion adds `build_id`. This avoids a circular hash. The id file is a convenience assertion, never evidence by itself. MD5 here detects accidental changes; this is not an authenticity/signature scheme.

### Exact logical keys

All fields below are non-null. `build_id` is a 64-character lowercase hexadecimal string; all other names/ids marked text are UTF-8 strings with exact, case-sensitive equality. In each individual snapshot, omit the physically repeated `build_id`; prefix every primary and foreign key with it when combining releases.

| Table / physical file | Columns defining identity and linkage | Uniqueness and scope |
|---|---|---|
| Record catalog / `te_loci.tsv.gz` | `locus_id:text`; `chrom:text`, `start:int64`, `end:int64`, `strand:enum(+,-)`, `subfamily:text` (= repName), `family:text`, `class:text` | PK `(build_id,locus_id)`; also UNIQUE `(build_id,subfamily,chrom,start,end,strand)`. Taxonomy FK is `(build_id,subfamily,family,class)`. |
| RepeatMasker grouping membership / `repeatmasker_groups.tsv` | `rm_id:int64`, `locus_id:text` | PK `(build_id,rm_id,locus_id)` and UNIQUE `(build_id,locus_id)`; each fragment belongs to exactly one source group. Group identity is `(build_id,rm_id)`; assert all its members share one contig. No redundant group-header table. |
| Taxonomy dimension / `te_dim.tsv` | `subfamily:text`, `family:text`, `class:text` | PK `(build_id,subfamily,family,class)`; every record references exactly one row. No uniqueness assertion on subfamily alone. |
| Universe membership / `universe_membership.tsv` | `universe:text`, `locus_id:text` | PK `(build_id,universe,locus_id)`; locus FK to catalog; universe FK to the manifest's predicate map. A fragment may belong to several universes. |

**Premise:** filtering currently happens before identity assignment (T/src/10_build_master.sh:27–49), while the owner wants preserved annotation and explicit policy views (O:15–19). **Implication:** make the catalog cover the full matched source record set; apply filters in universe membership and exports. The ledger reads the catalog independently of peak overlap; exporters and ledger selections read membership. **Caveat:** this enlarges the catalog; only materialize universes actually selected for the owner's analysis or its declared sensitivity comparisons, not every imaginable subset. The whole catalog needs no duplicated `all` membership rows.

Keep the existing 1-based inclusive component columns and form `locus_id = subfamily + '|' + chrom + ':' + decimal(start) + '-' + decimal(end) + '|' + strand`, as currently emitted (T/src/10_build_master.sh:25,41–49). Assert this equality, `1 <= start <= end <= contig_length`, and selfdesc uniqueness. Generate BED start as `start-1`; never recover coordinates by splitting the string. Canonical ids retain UCSC component names when an export uses aliases. Reject reserved delimiters/whitespace rather than silently escaping names; revisiting that restriction would be a schema change. **Premise:** coordinate-only keys collide in the audited full source (A:122–123). **Implication:** repName remains part of identity. **Caveat:** a renamed repName changes identity and needs an explicit cross-release mapping.

**Premise:** the source `.out` supplies genuine grouping ids, and a group can contain several repNames; the audit explicitly limits their structural interpretation (A:39–45,126–127). **Implication:** join `.out` to the catalog on normalized `(chrom,start,end,repName)`, assert one-to-one complete coverage and strand agreement, then emit membership. Retain the original source files for later consensus-coordinate/structural investigation. **Caveat:** `rm_id` is scoped to this release, not a stable biological insertion accession. Sum covered blocks as interval unions; a group's min–max span includes gaps and is not its TE sequence. Do not assign one taxonomy triple or one inferred count to every group member.

**Premise:** the builder already groups taxonomy by the full triple (T/src/10_build_master.sh:55–59), but subfamily-only joins duplicate ambiguous names (A:48–54). **Implication:** keep the triple as the dimension key; direct subfamily RNA stays keyed by subfamily. Retain `n_loci:int64` and `total_bp:int64` as full-catalog triple summaries for validation/rollups; `total_bp` means summed record lengths, potentially overlapping. **Caveat:** a subfamily with several triples has unresolved family/class attribution; do not copy its count to each triple. Universe-specific summaries are computed through membership.

### Foreign keys in the owner's three tables

- `repeat_fragments`: PK `(build_id,locus_id)`; ingest the catalog components and annotations, regardless of overlaps.
- `peak_te_overlaps`: PK `(peak_set_id,peak_id,build_id,locus_id)` for ordinary single-interval peaks; fragment FK `(build_id,locus_id)`. Keep intersection coordinates/fractions as the owner specifies. Multiple overlap rows never become multiple copies of peak accessibility.
- `te_feature_registration`: mapping-row key `(analysis_run_id,feature_id,build_id,universe,resolution,catalog_object_id)`, with text ids and `resolution` restricted initially to `fragment`, `rm_group`, `subfamily`. `catalog_object_id` is respectively the exact `locus_id`, canonical decimal `rm_id`, or exact subfamily name. Validate its typed FK against records, distinct groups, or distinct subfamilies in the selected universe. This table supports one feature mapping to multiple objects; validate each feature's declared resolution is consistent. The analysis run pins the export path and md5.

**Premise:** these mappings express measurement support, and the owner requires conservation tests (O:37–42,51–57). **Implication:** all three carry **BUILD_ID**, with no annotation-id column; registration is a mapping, not a quantitative fact table. Test a many-member group and an ambiguous subfamily with one count each: joins must preserve each single count. **Caveat:** registration cannot create locus evidence from subfamily support; quantitative tables stay at their original measurement grain. Future genuinely reconstructed objects require their own definition before adding another resolution.

## 2. Manifest: only these fields

**Premise:** current counts are interpolated expectations, and fetching verifies three sources while FASTA remains declared (T/src/90_manifest.sh:43–47; T/src/00_fetch_sources.sh:14–20; T/config/mm39.env:26–30). **Implication:** serialize the following deterministic JSON with sorted keys, fixed separators and one terminal newline, using Python stdlib. The verifier, exporters and ledger loader are its readers. **Caveat:** build time and an alternative builder revision do not belong to an “identical rebuild”; changing builder SHA changes this strengthened release identity, even if data files match.

- `schema_version`: integer; defines columns, key rules, 1-based catalog coordinates, UCSC canonical namespace and fingerprint recipe.
- `assembly`: assembly name, e.g. `GRCm39`.
- `builder_sha`: full producing commit SHA. Require a clean producing tree for publication; local dirty trials remain staging-only because a SHA cannot reproduce their code.
- `sources`: keyed by role (`rmsk`, `repeatmasker_out`, `chromAlias`, `genome_fasta`, `chrom_sizes`, and `gene_gtf` only when a delivered view uses it); each has `url` and **observed** `md5`. Hash exact retained bytes, including compressed `.out.gz` and FASTA. Verify pins before processing. Verify chrom.sizes against lengths read from that actual FASTA, through the alias map where necessary. No invented `.out` md5: obtain it during the eventual authorized build and pin it before publication.
- `universes`: map from universe name to exact executable semantics: sorted `include_classes`, literal `exclude_family_prefix` (empty means no exclusion). Any later interval-subtraction/context view also records its actual predicate and input roles here when implemented. Name alone is never the policy definition.
- `counts`: observed full-catalog `records`, `contigs`, `subfamilies`, `triples`, `rm_groups`; for each delivered universe the same counts plus `by_class` record counts. Compute from finalized tables, including distinct groups among selected members. These are the owner’s validation and population-denominator readers.
- `outputs`: relative data-file path → `{md5}` for every delivered data file. It excludes the manifest to avoid self-reference; publication includes the manifest's own observed md5 in the BUILD_ID calculation. Require exact agreement between this map and files present, apart from `MANIFEST.json`, `BUILD_ID`, and `source/`.

Delete timestamp, snapshot tag, git-describe, redundant byte lengths and inactive policy knobs from the manifest. Retain sources for reconstruction, with the manifest carrying their checksums; remove the duplicate `source/SOURCES.json` receipt. Source retention is provenance, not another release identity.

## 3. Publication: directories and one public symlink

Layout: `te_mm39/.staging/<unique>/`, `te_mm39/archive/<64-hex-id>/`, `te_mm39/current -> archive/<64-hex-id>`. The archive is the permanent snapshot store, including the selected build. There is no separate move-on-supersession operation.

**Premise:** date-path reuse permits live overwrite, old-id trust permits misarchival, and publication currently updates several pieces of state (T/build.sh:43–51; T/src/release.sh:47–69; A:62–73). **Implication:** build privately and commit only complete immutable directories; use the symlink as the sole mutable public selector. **Caveat:** this assumes one local filesystem with atomic rename semantics and cooperative publishers; it does not defend against an administrator editing published bytes. Checks detect such edits.

1. **Allocate a fresh staging directory under an explicitly passed family root.** Use `mktemp -d`; reject any attempt to build in a published path. Resolve/validate the family and staging paths. A date may appear in a temporary name but has no identity role. **Defends:** identical-date collision and failure midway; interrupted work can only leave private staging files.
2. **Build and validate only there.** Write the manifest afresh after tables finish; check source hashes, keys, joins, bounds, observed counts and selected expectation files. Remove work files before inventorying outputs. Verification uses temporary storage outside published snapshots. **Defends:** failed builds and stale manifests. The current verifier writes `.class_observed.tsv` into the snapshot (T/src/99_verify.sh:49–57); stop that before calling snapshots immutable.
3. **Recompute the inventory, every md5 and BUILD_ID from bytes.** Check exact file-set equality, not just listed files (the present check iterates manifest entries only: T/src/99_verify.sh:20–33). Write the convenience `BUILD_ID` only in staging. **Defends:** a newly added output silently retaining an old id. Adding any output requires a new complete staging build; never append to a published directory.
4. **Validate any existing `current`.** It must be a symlink to a complete directory inside the permitted family layout, whose recalculated identity agrees with its manifest, id file and hash directory name. A regular file/directory at `current`, dangling link, escaping target or checksum mismatch is corruption: abort publication, retain the candidate, report the precise discrepancy, and leave existing evidence untouched. **Defends:** corrupt-current acceptance and archiving corrupted bytes under their claimed old id. Recovery is an explicit local repair: verify a candidate independently, preserve any damaged directory in place for diagnosis, then atomically replace the selector with that verified candidate. Never relabel damaged bytes as a valid old snapshot. A damaged old id resolves only after restoring its original verified bytes.
5. **Install at `archive/<full-id>` with one same-filesystem directory rename.** Use Python `os.rename`, not shell `mv` with directory-nesting semantics. A published destination is always nonempty. If an identical-id publisher already installed it, rename fails: verify the existing directory from bytes, then discard only this process's redundant staging directory. If the destination is malformed, abort; never overwrite it. **Defends:** concurrent identical builds and crash during installation. A complete unselected archive directory after interruption is harmless and reusable.
6. **Select using atomic symlink replacement.** If verified `current` already names this id, finish without changing it. Otherwise create a private temporary symlink in this process's staging area pointing to `archive/<id>`, then Python `os.replace` it onto the family’s `current`; the relative target is interpreted at its final location. Remove this process’s empty staging area. **Defends:** readers seeing a missing pointer and two different concurrent builds. Both complete snapshots remain; the last successful pointer replacement wins. No promise of launch-time ordering. Readers resolve `current` once, then use the immutable resolved directory for all files.

There is one persistent symlink; the temporary replacement link exists only during the commit. No locks are needed because archives never move and concurrent installation converges by full id. Same-date changed annotation yields another hash directory; same-date identical rebuild deduplicates. A process death before selection leaves the previous selection valid; a death after selection leaves the new complete snapshot valid. Sudden machine/storage power-loss durability additionally requires file and directory `fsync` in the Python publication helper; atomic visibility alone does not promise that stronger guarantee.

**Stop doing:** trusting the old `BUILD_ID` file (T/src/release.sh:47–58), deriving the family as `dirname "$SNAP"` (T/src/release.sh:16–17), reusing date destinations, retaining an existing manifest (T/src/90_manifest.sh:13–17), and moving old snapshots. Pass the actual family root explicitly; `dirname` of a nested staging path would archive into staging.

## 4. Expectations without a framework

**Premise:** shape expectations live in genome config and class fixtures are selected by genome (T/config/mm39.env:64–70; T/src/99_verify.sh:40–54). **Implication:** move `EXPECT_*` into a simple `shape.env` beside `class_counts.tsv` under `tests/expectations/<rmsk-md5>_<out-md5>/<universe>/<predicate-sha256>/`. Compute the predicate hash from the same canonical universe JSON used in the manifest. Keep full-catalog checks under reserved `catalog/` with its schema version. The existing shell assertions and `diff` remain the readers; require the selected fixture rather than silently skipping it. **Caveat:** fixtures require independently reviewed measurements, never auto-accept the current build's observations. Include another source checksum in the directory key only when a tested view depends on it, e.g. GTF for exon subtraction. Predicate hashes are fixture lookup keys, not another ledger identity.

A universe change adds its own fixture directory and leaves genome-keyed source pins alone. Keep six small publication smoke cases corresponding to steps above, in the existing test style; no runner, registry service or generated expected-output machinery is needed.

## 5. What a consumer pins

A consumer resolves `current` once and records the full BUILD_ID plus relative paths and md5s of every file it actually uses, including `MANIFEST.json`; it verifies the complete inventory and recomputes the id on acquisition, then loads all files from that resolved snapshot. Ledger keys carry that BUILD_ID. After supersession, the same id resolves directly as `<reference-root>/te_<genome>/archive/<BUILD_ID>/`, with no date, mutable index or symlink lookup. Transfers preserve that directory and are verified at destination. Legacy snapshots using the old manifest-excluding recipe retain that recipe when imported, are checked from bytes before being placed under their original full id, and receive no in-place format upgrade; absence of `schema_version` identifies this legacy contract. A corrupted legacy snapshot cannot be imported successfully under its claimed id. The pin guarantees the checked bytes, while feature resolution determines which biological joins are justified.

**Premise:** `INDEX.tsv`, `CURRENT_BUILD.tsv` and `current` repeat publication state (T/src/release.sh:52–69; T/docs/RELEASES.md:30–40). **Implication:** delete both TSVs, reconfirmation receipts, short-id archive names and date-based release naming; the full-id directory resolves history and the manifest supplies provenance. **Caveat:** there is no chronological promotion log; the owner's consumer pin supplies the relevant analysis history.

**Premise:** the builder supports an alternative ordinal id and emits `dup_index` for compatibility (T/src/10_build_master.sh:38–49), while exports remain planned and the owner requests only needed, parser-tested ones (A:13–15; O:17–19). **Implication:** delete `LOCUS_ID_FORM`, its ordinal branch, and universal `dup_index`; generate any necessary ordinal inside the specific export and register it. Replace the misleading `rmsk_id` column with genuine `.out` membership; retain raw UCSC bytes in `source/`. Remove unused `INTERGENIC_MIN` and `EXPECT_LOCI_NOEXON` until their readers exist (their intended readers are described at T/config/mm39.env:50–54,69–70). **Caveat:** an ordinal export will change when its universe changes, so its exact file checksum and registration are essential. A second annotation identity, materialized group spans, a taxonomy surrogate-id registry and a release database add maintenance without a reader required here; omit them.
