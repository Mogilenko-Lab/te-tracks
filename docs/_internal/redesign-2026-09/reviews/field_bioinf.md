# Field review: methods and conventions (bioinf)

*Read-only review. Classification counts cited below are read from the existing mm39 build already present at `/workspaces/Meta-Aging/_scratch/te-tracks-audit/refroot/te_mm39/build` (queried via pandas against `tables/rmsk_taxonomy.tsv`); no build, install, quantifier run or git command executed this session.*

## Verdict on the drafted direction (sound / amend / reconsider), one paragraph

Sound, with documentation amendments rather than design changes. The drafted mask (`all_exons_unstranded_union_v1`), the deferred sparse record×transcript context relation, the separation of "te-tracks ships pinned geometry, consumers derive versioned labels" (G5/C5), and the H3 ruling that `exon_subtraction_status=unchanged` must never seed `gene_context` are all methodologically correct and, on the context-relation geometry, more careful than the field's own default convention (ChIPseeker/HOMER pick one nearest gene with silently broken ties; the draft keeps every tied isoform and every simultaneous exon/intron/promoter relationship explicit). The classification layer needs surfacing, not redesign: the specific field-contested mappings the owner asked about (B1 filed under RepeatMasker family `Alu`, MaLR spelled `ERVL-MaLR`, ERV internal/LTR pairs as separate records under one family) are already correctly worked out in this project's own internal consult notes (`consults/{SYNTHESIS,ADR2_consult,B_taxonomy_universes,FINAL_REPORT}.md`) but have not reached the published contract (`docs/OUTPUTS.md`, `docs/DECISIONS.md`) a downstream consumer actually reads. On counting, the dissertation/TEsingle lineage gives an already-actionable answer — locus-level EM over subfamily metagenes — that nothing in the plan currently states as a consumer-facing recommendation. The one lens genuinely unresolved by any party in scope, not just te-tracks, is gene-TE multi-annotating reads: no vendored tool solves it, and the exon-subtraction guarantee is correctly scoped to exon-disjoint support rather than molecule exclusivity.

## Findings

- [F1] Mouse B1, the single largest SINE family (558,808 records, 15 `rmsk_name` subfamilies: `B1_Mus1`, `B1_Mm`, `B1F`, `PB1D*`, …) carries RepeatMasker `repFamily = "Alu"` in the pinned mm39 source, not "B1" — measured this session from `tables/rmsk_taxonomy.tsv`, corroborating `consults/FINAL_REPORT.md:77-82` and `consults/ADR2_consult.md:42,86` ("mouse B1 records already carry the RepeatMasker family label `Alu`") — a consumer reading only `docs/OUTPUTS.md`'s `family.bed` section or `docs/DECISIONS.md` has no way to know this, so filtering `family.bed` column 4 for "SINE/B1" silently returns zero rows — add a short "RepeatMasker family-label surprises" note to `docs/OUTPUTS.md`'s `family.bed` section — phase 4/docs, no code change.
- [F2] "MaLR" never appears as a standalone `rmsk_family`; it is always the hyphenated `ERVL-MaLR` (534,111 records, the largest LTR family), matching the general RepeatMasker/Dfam convention of concatenating Wicker et al.'s (2007, *Nat Rev Genet* 8:973-982) superfamily and family into one string (`hAT-Charlie` 105,223, `hAT-Tip100` 13,741, `TcMar-Tigger` 27,962 records, same query) — te-tracks' two-rung `taxonomy_canonical` (`canonical_class`, `canonical_family`) is a defensible collapse of RepeatMasker's three raw tokens onto the field's five-rung scheme (class/subclass/superfamily/family/subfamily, per the dissertation's own `HERVK9-int_dup720` worked example), but the hyphen is the only place the superfamily rung survives and no column or doc currently says a consumer should split on it — `docs/OUTPUTS.md` taxonomy_canonical section, phase 3/docs.
- [F3] ERV internal and LTR regions are cataloged as separate records under one family (e.g. `IAPEz-int` alongside `IAPLTR1a_Mm`, both `rmsk_family=ERVK`); `consults/SYNTHESIS.md:49-52` already measured that the commonest `rm_instance` (`.out`-ID) mixed-name groups on chr1 are exactly these LTR-plus-internal pairs — DECISIONS.md's recorded deferral ("ERV units: the instance relation and consensus coordinates are prerequisites; validated LTR-internal membership defines the unit later") is correctly scoped, and the field's standard tool for this reconstruction, "One code to find them all" (Bailly-Bechet et al. 2014, *Mobile DNA* 5:13), explicitly prioritizes assembling full `LTR-I-LTR` elements before falling back to solo-LTR or internal-only pieces — cite it as the target algorithm when that deferral is picked up, since `rm_instance` grouping alone bounds gaps and nested elements without validating an LTR-internal pair — recorded deferral, structural stage.
- [F4] The dissertation's own synthetic benchmark found subfamily "metagene" tools (scTE, SoloTE) are the two worst performers on TE accuracy and that locus-specific methods "out-perform subfamily-level methods across the board," including subfamily-level aggregation of locus-specific results (`thesis_2023_excerpts.md`); this is now independently field-corroborated (scTE, He et al. 2021, *Nat Commun* 12:1456: subfamily-only by construction; Telescope, Bendall et al. 2019, *PLOS Comput Biol* 15:e1006453, and MATES, Wang et al. 2024, *Nat Commun* 15:8154: locus-specific by design) — te-tracks already ships the locus-level `record.gtf`/`record.bed` grammar and TEsingle is already a *required* consumer fixture (check 12), so the reference material supports naming locus-level EM as the default counting level, not treating it as one option among equals — Recommendations section below, no code change, phase 5/9.
- [F5] No consumer in scope solves gene-TE multi-annotating reads: the dissertation reports "near-zero accuracy on intronic TEs across all methods on both datasets," and even TEsingle's own paper frames its anchored-molecule gene/TE split as a per-cell heuristic prior (`te_frac`), not a resolved assignment — `docs/DECISIONS.md`'s "molecule exclusivity between gene and TE counts is a property of the joint counting run" is the methodologically correct way to state this limit and should stay exactly that modest; it is a field-wide open problem, not a te-tracks gap — Verdict-level, no phase change.
- [F6] H3's finding and its ruling (`R/m2_divergent.md:24-32`, `R/m2_rulings.md:95-97`: `exon_subtraction_status=unchanged` is indistinguishable from intergenic, so D2 must derive nothing from it) is the single most consequential correctness safeguard in the gene-child design for the snRNA use case — an intronic-vs-intergenic flip directly inverts the "passive transcription" question the whole thesis excerpt is organized around — this is already adopted correctly and should stay a hard constraint on any future convenience view (candidate G3/C3), not something a later phase quietly relaxes for size.
- [F7] Gene-body and transcript-body distance disagree for 2,073 records genome-wide and flip the bulk toolkit's 10 kb/20 kb adjacency calls for 500/98 records respectively (`gene_child_consult.md` Q6 measurement); the bulk Rung-2 window is explicitly defined as "distance from any gene" (`K/docs/LIMITATIONS.md:130`), not from a transcript, so carrying gene-body geometry alongside transcript-TSS/TES geometry (candidate G4/C4) is the correct fix for a real, already-quantified ambiguity, not new scope — affirm as sound, phase 8 context design session.
- [F8] MATES's automatic mouse reference route pins mm10/GENCODE vM10 (`consults/B_taxonomy_universes.md` §6, `Ref2csv.py:9-10`), one full assembly generation behind this programme's mm39/GENCODE-vM37 pin, and its "exclusive" reference removes whole TE records overlapping gene bodies then clips to 1000 bp (`build_reference.py:88-89,127-150`) — te-tracks' fixture-only MATES adapter is correctly scoped as "waits for a named consumer" (`docs/OUTPUTS.md`), but if MATES is adopted for real, its shipped mouse reference must be rebuilt from te-tracks' own mm39 catalog, not trusted out of the box — consumer-adapter note, no code change.
- [F9] Stellarscope, the single-cell extension of Telescope (Bendall et al. 2019) and the field's standard locus-level Bayesian-EM model for ERVs, shows an observed right-boundary overlap defect against te-tracks' own fixture (`0,1,1,1` versus expected `0,1,1,0`, `docs/OUTPUTS.md` consumer table, check 11) — since ERVs are the TE class most implicated in the aging/senescence literature and the likeliest headline result of this programme, a one-base boundary misattribution is worth tracking to an upstream fix or report before any ERV-locus claim leans on Stellarscope output, not left indefinitely as "unsupported."
- [F10] IRescue's paper (Polimeni et al. 2024, *NAR* 52:e93) frames the tool as TE-*subfamily* quantification via UMI-graph EM, but its checkout (`irescue/em.py`, `count.py`, read this session) is feature-grain-agnostic — it runs the identical UMI-graph-plus-EM machinery over whatever BED a caller supplies — matching te-tracks shipping both `record.bed` and `subfamily.bed` for it; state this explicitly in `docs/OUTPUTS.md`'s IRescue row so a reader doesn't assume IRescue is subfamily-only by the paper's framing alone.
- [F11] 5' capture disambiguating promoter-driven from passive TE transcription is sound in principle (`thesis_2023_excerpts.md`), but the dissertation's own experience with the 10x v2 5' kit was "extremely low coverage, truncated reads, and a high degree of RT primer inclusion"; this programme's "5' PE OCM v3" chemistry is 10x's newer GEM-X Universal 5' v3 line (OCM = On-Chip Multiplexing, unrelated to the 5'-bias question) and its TE-promoter-proximity behavior is untested in the literature found for this review — te-tracks can supply the needed per-record consensus-relative 5' coordinate (`consensus_start_1`/`consensus_left_bp`), but whether OCM v3 reads actually pile up near TE 5' ends is an empirical pilot question (a TE-locus analogue of a gene-TSS metagene/read-start-density plot), not something the annotation alone settles — flag as an open question, not a finding to fix.
- [F12] te-tracks already carries the raw material for a full-length/promoter-intact flag (`consensus_start_1`, `consensus_end_1`, `consensus_left_bp`, `query_left_bp`, phase 2) that the dissertation explicitly recommends for restricting to TEs likely to retain an intact promoter; mouse literature gives active young L1 as three subfamily groups (L1MdA/Gf/Tf) totaling roughly 10,000 full-length, potentially transcription-competent copies collectively (Sookdeo et al. 2013 lineage of mouse-L1 work) — DECISIONS.md's "curated evolutionary ages and full-length or ORF status wait for a structural stage" is a well-scoped deferral: the derivation is future work, but the columns it needs are already shipped.
- [F13] No vendored consumer processes ATAC fragments at TE-locus resolution — TEtranscripts/TElocal/TEsingle/Stellarscope/IRescue/MATES are RNA-only, and scTE's scATAC mode (He et al. 2021) is subfamily-metagene-only — the 14761-DM peak ledger's record-keyed interval design (already the "14761 ATAC route" in `docs/OUTPUTS.md`'s consumer table) fills a genuine gap in the tool landscape rather than duplicating an existing capability; D2's ask to count Tn5 cut sites "inside the intersection or full TE locus" rather than whole-fragment overlap matches standard practice (ArchR/chromVAR count insertions, not fragment spans) and should be stated as the counting convention in the ledger's own design note.
- [F14] Nested/overlapping TE copies are already a measured, tracked property of this catalog (30,569 mixed-name `rm_instance` groups covering 95,830 records, `docs/OUTPUTS.md` phase-4 registration section), directly validating D2's "summing locus counts will double-count nested copies" concern; the peak ledger should join through `tables/export_feature_members.tsv.gz` (per-block membership) rather than `tables/rmsk_records.parquet` directly, so it inherits this de-duplication instead of re-deriving it.
- [F15] The 14761-DM spleen Multiome design (one pooled library per condition, 3 mice pooled inside, no biological replicate, no Rapa+MetR arm) has zero degrees of freedom for between-condition variance at any feature grain; per the pseudoreplication literature (Squair et al. 2021, *Nat Commun* 12:5692; Zimmerman et al. 2021, *Nat Commun* 12:738), even correct pseudobulk aggregation collapses to n=1/condition here, so only descriptive effect sizes are defensible for TE-level claims from this arm — the paired 20-animal design (14616 spleen + 14782 lung, 4 true biological replicates/condition, joined on `MouseID`) is the one arm that licenses an actual TE-level hypothesis test, and low per-locus TE counts (versus gene counts) make a single pooled library's sampling noise easier to mistake for a condition effect, so this asymmetry matters more for TE claims than for gene claims — Recommendations section below.

## Field conventions table

| question rung | primary tool(s) | counting level | multi-annotating treatment | context metadata used |
|---|---|---|---|---|
| class/subclass/superfamily/family/subfamily rollup | RepeatMasker/Dfam library curation (Wicker et al. 2007 convention) | n/a — annotation, not counting | n/a | raw `repClass`/hyphenated `repFamily`/`repName` triple only |
| ERV internal/LTR unit reconstruction | "One code to find them all" (Bailly-Bechet et al. 2014) | locus, post-assembly | LTR-I-LTR assembled first, solo/internal-only as fallback | consensus coordinates, `.out`-ID grouping |
| subfamily "metagene" quantification | scTE, SoloTE | subfamily | whole-locus removal at index time (scTE exclusive/nointron) or random single-alignment pick; no gene-gene or TE-TE ambiguity handling documented | none |
| locus-specific EM quantification | TEsingle, STARsolo-EM, Alevin-Fry | locus (subfamily/family carried as attributes) | EM over the cell's full gene+TE feature space; anchored ambiguous gene/TE reads split by a per-cell heuristic prior | none (TEsingle: full transcript-span gene model only) |
| locus-specific Bayesian reassignment | Telescope / Stellarscope | locus | Bayesian mixture EM, TE-only competition, greatest-overlap threshold pre-filter | none |
| locus-specific deep-learning allocation | MATES | locus | autoencoder+MLP on flanking-read context; gene-overlapping records removed at reference-build time, not at read-assignment time | gene-body exclusion (reference-build only) |
| gene/TE read-priority heuristics | TEtranscripts (subfamily), TElocal (locus) | subfamily or locus | "unique read prior to gene, multi read prior to TE"; gene index is exon rows only, so intronic TE reads default to the TE | none |
| UMI-graph + EM, grain set by input BED | IRescue | subfamily (as published) or locus (as te-tracks ships it) | UMI-graph dedup, then EM over ambiguous equivalence classes | none |
| genic-context labeling of a TE/peak locus | TE-Seq (Exonic/Intronic/Intergenic, per this programme's toolkit notes); ChIPseeker/HOMER (Promoter-TSS/Exon/UTR/Intron/Intergenic + signed TSS distance) | n/a — annotation layer | n/a | exon/intron/intergenic label, or nearest-gene + signed distance, both usually single-winner not sparse |
| te-tracks (this build) | reference layer for all of the above | record/subfamily/family/taxonomy_triple selectable via `export_feature_members` registration | left to the consuming quantifier; exon-subtraction removes double counting, not ambiguity | exon-subtracted mask shipped; sparse record×transcript relation deferred past phase 8 |

## Recommendations by dataset

- **14616-DM spleen + 14782-DM lung** (5' PE OCM v3, whole cells, 4 true biological replicates/condition, per-mouse, matched spleen-lung pairs): use locus-level EM as the primary counter — TEsingle is already a required te-tracks fixture and is the dissertation lineage's own recommendation — with subfamily/family rollups as secondary descriptive summaries via the same registration join, not a separately-run tool. This is the one dataset pair where a TE-level aging call can be asked to replicate across two tissues in the same animal (F15); design the analysis to require that replication before treating a spleen- or lung-only TE hit as a claim.
- **14761-DM spleen Multiome, RNA side**: use the same locus-level tool family against the cellranger-arc GEX BAM if per-nucleus CB/UB tags are exposed; GeneFull-style full-transcript gene counting is already standard for snRNA-seq given ~40% intronic content (TEsingle paper). Treat every condition-level comparison from this arm as descriptive only (F15) — do not report a TE-level p-value from this arm alone; use it to corroborate direction from the paired 20-animal arm.
- **14761-DM spleen Multiome, ATAC side**: build directly on te-tracks' `record.bed` plus the (currently deferred) context relation, using Tn5 cut-site counting inside the overlapping interval (F13); do not adapt an RNA-side tool, since none of the seven vendored consumers offers locus-resolved scATAC TE counting. Prioritize delivering the context relation's TSS/TES + promoter geometry for this consumer specifically — D2's schema already names `gene_context` as its blocking dependency.

## Open questions for the owner

- Should `docs/OUTPUTS.md`/`docs/DECISIONS.md` carry an explicit "RepeatMasker family-label surprises" note (B1→`Alu`, MaLR→`ERVL-MaLR`) so a consumer doesn't need to read the internal consult archive to avoid a silent zero-row filter (F1)?
- Is TEsingle the programme's anointed default TE counter for the two whole-cell 5' datasets (F4), or should STARsolo-EM/Alevin-Fry stay live as alternatives pending a local benchmark on real data?
- For the deferred context relation's promoter window `(U, D)`: one fixed pair, or a small family of named windows matching the bulk toolkit's existing 10 kb/20 kb adjacency bands, so downstream consumers aren't reinventing incompatible windows?
- Does the ATAC side's total absence of a locus-resolved vendored TE tool (F13) raise the priority of the context relation's delivery relative to phase 8/9's current ordering?
- Should MATES stay a "waits for a named consumer" fixture given its automatic mouse reference is a full assembly generation behind this programme's pin (F8), or is building a from-scratch mm39 MATES reference in scope for whoever adopts it?
- Should the program record a named, explicit statistical policy (e.g., "descriptive only below n=2 pooled libraries per condition") somewhere in the cross-dataset docs, so a future consumer doesn't run a per-cell test against the Multiome arm's condition-level design (F15)?
