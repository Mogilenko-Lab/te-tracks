## Blocking

- **[B1] docs/RELEASES.md:145-146 — three per-namespace export sums and the payload total are wrong against disk.** The doc carries `ucsc` 3,021,713,838 / `ensembl` 2,926,268,559 / `gencode` 3,021,138,299 and a total of 10,461,962,113. Summing the manifest's own inventory bytes (cross-checked against `stat -c %s` on all 43 files, 0 mismatches) gives **3,021,714,346 / 2,926,266,953 / 3,021,140,740** and **10,461,884,289**, i.e. deltas of +508 / −1,606 / +2,441 and −77,824. The three namespace figures match neither the file sums nor `du -sb`; the total is exactly payload + 19 directory entries × 4,096, so it is a `du` tree size presented as a payload sum in a sentence that excludes even the identity files ("per build before the child family and identity files"). The implementer reported this as deviation 3 rather than editing the plan, which was the right call under its prompt — so this is the document, not the implementation. Fix: publish the measured file sums with the measurement named (`sum of regular file sizes`), and if a provisioning figure is wanted alongside, give `du -sb` separately (10,462,001,814 for the whole build directory). Registration 347,526,106 is correct and needs no change.

## Advisory

- **[A1] src/lib/manifest.py:346,357 — verification is locked to the producing checkout's contract constants, and `select` has no route past a superseded selector.** `verify_build` asserts `taxonomy_rule_version == TAXONOMY_RULE_VERSION` and rebuilds `export_contracts` from the live `EXPORT_JOBS`/`EXPORT_CONTRACTS`. Demonstrated on a scratch copy with `TAXONOMY_RULE_VERSION = "taxonomy_rule_v2"` against a root holding v1 archives: `verify-current` exit 1, `select --build-id <any>` exit 1, `install --select` exit 1 (`unsupported taxonomy_rule_version`, naming the *existing* archive), while bare `install` exits 0. So the first taxonomy-rule or export-roster bump blocks selection at every root until `current` is removed by hand, and a destination running a different checkout rejects a valid transferred archive. The rejection itself is what ADR67 §3 asked for; the gaps are (a) `select_locked` verifying the outgoing selection with the same version gate as the incoming one, and (b) `docs/RELEASES.md` never stating that verification is version-locked or how to re-select across a bump.
- **[A2] src/lib/manifest.py:139-141 — `identity.catalog.sources` covers all four sources, so a contig-alias refresh mints a new `CATALOG_ID` with an unchanged record catalog.** `chromAlias` and `chrom_sizes` feed namespace exports and bounds checks, not record content; `chrom_sizes` is already pinned at build scope as `contig_set_sha256`. If UCSC republishes `mm39.chromAlias.txt` (they have added columns before), the next build has byte-identical `rmsk_records.parquet`, `rmsk_records.tsv.gz`, `rmsk_instance_members.tsv.gz` and `rmsk_taxonomy.tsv` and a different `CATALOG_ID`, and every consuming ledger row keyed on `(te_catalog_id, rmsk_record_id)` stops joining — the exact continuity H5 created `CATALOG_ID` to protect. Narrowing `catalog.sources` to `rmsk_out` (the source that produces records) restores it. The plan's own wording ("source digests") is what the implementer followed, so this is a contract amendment, not a defect against the prompt.
- **[A3] src/release.py:85-88 — `select` verifies two full archives, and re-selecting the current id verifies the same one twice.** Counted with a call-counting wrapper: 2 full `verify_build` entries per `select` in all three cases (already-selected, different id, back again). On mm39 that is ~21 GB of hashing (~52 s warm, minutes cold) to re-affirm a correct selector. The `existing_id` plumbing `install` already uses would let `select_locked` skip the second pass when the resolved target is the candidate.
- **[A4] src/release.py:78 — a dangling selector is reported as an archive fault.** Removing the selected archive directory outright correctly blocks `select`, `install --select` and `verify-current` (exit 1, selector and staging preserved), but the message is `invalid archive target: .../archive/<id>` with no mention that the path came from resolving `current`. An operator reads an archive error for a selector fault. Wrapping `verify_current`'s call in a selector-scoped message would fix it.
- **[A5] src/lib/build_exports.py:29-46 — `EXPORT_CONTRACTS` is keyed by filename, so consumer attribution cannot vary by universe, and two entries over-claim.** `exports/<ns>/interspersed/full/record.bed` carries `"14761 ATAC"`, whose route (m5 H2) is the `all_rmsk` copy; `exports/<ns>/all_rmsk/full/record.bed` carries `IRescue` and `bedtools`, which only the interspersed copy's fixtures exercise. Everything else in (f) is truthful — see the agreement note below.
- **[A6] docs/RELEASES.md:149 — the host-floor figure is a stale unit-slipped restatement.** `5,891,116 KiB` is 6.03 GB / 5.62 GiB, not "5.9 GB"; and this build's own provenance records `peak_rss_bytes = 5,968,367,616` (5,828,484 KiB) for stage 30. The doc attributes its figure to the phase-6 fix verification, so it is traceable, but it neither matches the installed archive's provenance nor points a reader at `provenance.peak_rss_bytes` for the per-build number. `3,853,776 KiB` for stage 35 is unverifiable from this build: `build.sh` instruments `30_*` alone.
- **[A7] src/lib/manifest.py:229-237 — the recorded "devcontainer image identity" does not identify the devcontainer image.** Of seven probed paths only `/etc/cloud/build.info` exists (`serial: 20260627`), plus `/etc/os-release` (Ubuntu 22.04.5). `status` says so honestly, but `docs/RELEASES.md`'s instruction to "run host builds inside the same devcontainer image" has nothing in the manifest to compare against; the four toolchain versions are the actual comparable evidence and deserve that sentence.
- **[A8] tests/checks/core/72_publication_cases.py — cases not covered.** Uncovered by 72 (all pass when I drive them myself): `install --select` against a broken `current`; a genuinely removed archive directory under `current` (72 forges the symlink instead, same code path); `current` as a regular file, a directory, or an absolute symlink (all exit 1, named); staging outside `family/.staging`; a non-hex `--build-id`; `archive/` present as a regular file; a symlinked family root. Structurally untestable in one container and uncovered everywhere: the `st_dev` cross-filesystem guard at src/release.py:135. Also 72's "new export" case adds a plain payload file rather than an export path — the identity boundary is the same, and I confirmed the true added-export case in (b).

No contrastive negation anywhere in the phase-7 hunks of `README.md`, `docs/RELEASES.md`, `docs/OUTPUTS.md`, `docs/DECISIONS.md` (the two `never` hits in OUTPUTS.md are pre-existing lines 230 and 438).
